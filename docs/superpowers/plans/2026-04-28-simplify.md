# VoteScot simplification plan

Date: 2026-04-28

This plan synthesises findings from a parallel review across six facets of the codebase: Astro pages, React components, the data layer, quiz/matching utilities, scripts and CI, and tests/validation. The goal is to reduce surface area before the 7 May election, not to redesign anything. Phases are ordered by value-to-risk ratio and are independently shippable.

The headline themes the audits surfaced:

- Party metadata (color, accent, label, partyShort) lives in three or more places, and the keys are inconsistent ("lab" vs "labour", "con" vs "conservative") — a latent bug.
- Per-candidate YAMLs duplicate party-level positions and stances byte-for-byte (e.g. `data/candidates/anas-sarwar.yaml:24-59` vs `data/parties/scottish-labour.yaml:3-20`), creating a dual source of truth with no consistency check.
- Three implementations of postcode lookup coexist (`PostcodeLookup.tsx`, `PostcodeInput.tsx` + `usePostcodeLookup.ts`, and an inline copy in `ConstituencyMap.tsx:342-381`), and two of them ignore the hook.
- Several scripts under `scripts/` are one-off bootstrap or migration tools that have already done their job.
- Test coverage has clear gaps in data loaders, the postcode hook, and `poll-average` edges, alongside a small number of duplicative tests.

## Phase 1: Dead code and quick wins (shipped 2026-04-28)

Deleted the one-off ingestion and migration scripts that are no longer invoked by `package.json` or workflows: `scripts/enrich-candidates.ts`, `scripts/reconcile-candidates.ts`, `scripts/populate-projections.ts`, and `scripts/cross-copy-bios.ts`. The audit also flagged `apply-party-positions.ts` for deletion, but it is actively used by the `/sync-manifestos` slash command and the manifesto fan-out workflow, so it stays.

Cached `loadResources()` (`src/lib/data.ts:239-242`) the same way its sibling loaders are cached. Flattened `src/lib/party-match.ts` to a direct reverse lookup map, dropping the redundant per-id loop.

Three originally-planned items were dropped on closer inspection. The `PARTY_KEYS` export in `src/lib/poll-average.ts:129` is imported by `scripts/project-from-polls.ts`, contrary to the audit. The `loadManifestoRegistry()` missing-file fallback would silently degrade to a manifesto-less site if the registry ever went missing — better to crash loudly, since the file is fundamental to the build. The `stances` schema "contradiction" is actually the deliberate "all-or-nothing optional" pattern: stances may be absent, but if present, all eight policy areas must be filled. That is the semantics we want for the quiz.

The single comment in `src/components/NewsList.astro:14` containing an em dash is the only remaining one in the repo and is not user-facing. Leave it.

## Phase 2: Centralise party metadata

This is the highest-leverage change. Today every candidate YAML carries `color`, `accent`, optional `textColor`, and `partyShort`, which means 73 SNP candidates each repeat `#FDF38E` and rebrand requires editing dozens of files. The same fields are also redeclared inline in `src/components/ConstituencyMap.tsx:58-76`, `src/components/PollsChart.tsx:30-38`, and `src/pages/guide.astro:23-41`, with the additional hazard that the polling table uses `lab`/`con`/`libdem` while the map uses `labour`/`conservative`/`libdem`.

Move party theming into a single `src/lib/party-config.ts` keyed by canonical party id, sourced from `data/parties/*.yaml` (extending the party schema to include `color`, `accent`, `textColor`, `short`, `label`). Have `src/lib/data.ts` enrich candidates at load time by joining on the canonical party id rather than reading colors from each candidate YAML, and remove those four fields from the candidate and regional-candidate schemas. Decide on one canonical key set (the candidate-page convention `snp/lab/con/libdem/green/reform/alba` is already used in 73 candidate files and in `polls.json`, so prefer that) and update `ConstituencyMap.tsx` to match.

While the per-candidate `positions` and `stances` overrides should remain supported for the rare case where a candidate diverges from the party line, the default path should fall back to the party file rather than copy it. A small invariant test in `tests/` should fail when a candidate's `positions` or `stances` is byte-identical to its party's — that is duplication, not divergence, and indicates the YAML is wrong.

This phase touches every candidate YAML so it should land in two commits: one schema/loader change with a build-time backfill of colors from party files, and one bulk YAML edit removing the now-redundant per-candidate fields.

## Phase 3: Lift shared UI constants and helpers into lib

The competitiveness and status maps in `src/pages/candidates/constituency/[id].astro:24-48` and the `externalSources` filter duplicated in `src/pages/candidates/[id].astro:21` and `src/pages/candidates/regional/[id].astro:15` should move to `src/lib/candidates.ts` (or similar). The `democracyclub.org.uk` exclusion URL is a magic constant that belongs alongside them.

The same Astro pages render the candidate-detail shell — header with party badge, breadcrumb, bio, policy positions, track record, sources — almost identically (`src/pages/candidates/[id].astro:55-79`, `src/pages/candidates/regional/[id].astro:43-67`, `src/pages/candidates/party/[id].astro:61-83`). Extract a `PolicyPositions.astro` component and consider a `CandidateDetailShell.astro` layout the three pages can wrap, parameterised by which context fields they show.

## Phase 4: Consolidate postcode lookup

`src/components/PostcodeLookup.tsx`, `src/components/PostcodeInput.tsx`, `src/lib/usePostcodeLookup.ts`, and the inline lookup in `src/components/ConstituencyMap.tsx:342-381` are four implementations of the same MapIt query. Make `usePostcodeLookup` the single source of truth, rewrite `PostcodeInput` to consume it (already does), retire `PostcodeLookup` either by deleting it or making it a thin wrapper that delegates to `PostcodeInput`, and refactor the inline `ConstituencyMap` lookup to use the hook. Add the missing tests for `usePostcodeLookup` covering the success path, the not-found path, and the boundary case where MapIt returns an SPC area but no SPCF area.

`CandidatesSearch.tsx` is a thin wrapper around `SearchFilter` and `PostcodeInput`. If it's only used in one place, inline it; if not, leave it.

## Phase 5: Tame the big components

`ConstituencyMap.tsx` is 623 lines and has two large callbacks with eleven dependencies each (`onEachFeature` at lines 254-340 and `styleFeature` at 187-252). Split the three branches of `styleFeature` into pure builder functions (`regionStyle`, `projectionStyle`, `coverageStyle`) and the inline tooltip generation in `onEachFeature` into utility functions. This both reduces dependency churn (fewer items in the dep arrays means fewer needless GeoJSON re-renders) and makes the branches independently testable.

`ViewToggle.tsx:8-11` toggles visibility via `document.getElementById` and `style.display`. This is brittle: rename one of the IDs `view-constituency` or `view-party` in `candidates/index.astro` and the toggle silently breaks. Lift the visibility state into `candidates/index.astro` using Astro's `client:load` parent or convert the two views to conditional rendering inside a single React island.

`src/lib/quiz-helpers.ts` is 132 lines mixing party-block construction, constituency/region mapping, and URL parsing. Split into `party-blocks.ts`, `constituency-mapping.ts`, and one URL helper, or fold the URL helper into `QuizEngine`. Extract the magic threshold "answer at least 3 questions" (`src/components/QuizEngine.tsx:411`) to a named constant and add a test asserting submit is gated.

The duplicated window sorting in `src/lib/poll-average.ts:51-52` and `:84-85` should share a `getRecentWindow()` helper. The score formula `diff === 0 ? 100 : diff === 1 ? 50 : 0` in `src/lib/matching.ts:28` should be a named function (`diffToScore`) so the UI styling logic in `QuizEngine.tsx:290-295` can refer to the same scale rather than re-encode it.

## Phase 6: Tests and validation

Add tests for the loaders that have none (`loadConstituency`, `loadRegionalCandidates`, `loadResources`, `loadNews` in `src/lib/data.ts:100, 191, 239, 298`), for `usePostcodeLookup` (currently zero coverage), and for the empty-window edges of `rollingAverage` and `rangeOverWindow`. Add the candidate-vs-party duplication invariant from Phase 2.

Consolidate the duplicative caching tests in `tests/data-cache.test.ts:21-28` and `tests/data-parties.test.ts:11-15`, and the duplicate "all 8 policy areas" assertion in `tests/parties.test.ts:44-55` and `tests/data-parties.test.ts:27-35`. Decide whether `tests/quiz-redirect.test.ts` adds value beyond a config smoke check; if not, drop it.

Add a schema-validation step against the real `data/polls.json` at build time, since `loadPolls()` is currently unvalidated and the polls JSON is hand-fed by an external sync script.

## Out of scope

This plan does not touch the Alba question (Alba remains as a polls-table column and projection key even though they aren't standing). That's a product decision, not a simplification, and the polling tracker may still report Alba shares.

It also does not propose a TypeScript port of `validate-data.ts`, a switch to a different schema validator, or any change to the Astro/React boundary. Those are larger structural changes that would not pay off before the election.

## Suggested sequencing

Phase 1 and Phase 6 (tests for what already exists) can be done in parallel by separate sessions. Phase 2 should land before Phases 3-5 because the centralised party config makes the rest of those edits smaller. Phase 3 and Phase 5 are independent of each other once Phase 2 is in. Phase 4 stands alone.

A reasonable cadence is one phase per session, opening one PR per phase, with the bulk YAML edit in Phase 2 split into its own PR for reviewability.
